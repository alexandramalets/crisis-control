## Этап 1. Backend: БД, авторизация, справочники (23.10 – 26.10)

- Модели SQLAlchemy и первая миграция Alembic по разделу 5 ARCHITECTURE.md.
- Начальное заполнение: роли, единицы измерения, группы и системные показатели из [ПЗ]: выручка, объём продаж, прибыль, дебиторская и кредиторская задолженность, запасы, денежные средства, денежные потоки от операционной, инвестиционной и финансовой деятельности — с направлением влияния.
- Авторизация: Argon2id, JWT access и refresh с ротацией, вход, выход, текущий пользователь, блокировка при подборе.
- Организации: CRUD с проверкой владельца.
- Единый формат ошибок на русском языке.

**Тесты:** unit — хеширование, создание и проверка токенов; integration — вход, обновление токена, выход, доступ без токена (`401`), доступ к чужой организации (`404`).

**Статус (22.10.2026): выполнено.** 35 таблиц, миграции 0001 (схема) и 0002 (справочники), проверены на PostgreSQL 18.1 (откат и повторное применение, отсутствие расхождений моделей и схемы). Авторизация: вход по логину или email, Argon2id, JWT с идентификатором сеанса, ротация refresh-токенов, выход, блокировка после 5 неудачных попыток, смена пароля, регистрация (выключена по умолчанию), команда `python -m app.cli create-user`. API организаций, наборов данных (создание через JSON; загрузка файлов — этап 2), чтения исследований и отчётов. Тесты: 87 (15 unit, 72 интеграционных на PostgreSQL); дымовая проверка через nginx `scripts/smoke_api.py` — 22 из 22.

## Этап 2. Backend: загрузка и проверка данных (25.10 – 28.10)

- Шаблон CSV и XLSX; разбор файла (pandas + openpyxl).
- Проверка структуры (BR-1, BR-8, SEC-2): обязательные столбцы, известные коды показателей, формат периодов, числовые типы, дубликаты, лимиты размера. Ошибки → `422` с перечнем строк и столбцов, в БД ничего не пишется. Пропуски → предупреждения (`dataset_issues`), набор сохраняется.
- Сохранение значений в «длинном» формате; SHA-256 файла; зашифрованная копия файла (AES-256-GCM).
- Эндпоинты наборов, значений, порогов, плановых значений.
- Демонстрационный набор `sample-data/` (≥ 36 месяцев, чтобы хватало истории для прогноза).

**Тесты:** корректный файл; файл с неверной структурой; файл с пропусками; неверный формат периода; превышение размера; повторная загрузка того же файла.

**Статус (22.10.2026): выполнено.** CSV и XLSX через backend (`openpyxl`, без выполнения формул). Сервисы: чтение файла, схема, предобработка, сохранение. Двухшаговый поток preview → validate → import. Ошибки (дубликаты, некорректные числа и периоды, пустой и неподдерживаемый файл) блокируют запись в БД (SEC-2). Пропуски сохраняются как NULL с предупреждениями. Исходный файл — AES-256-GCM в `DATA_DIR` и в `dataset_files`. Состав показателей определяется файлом. Тесты: 109 (включая загрузку CSV/XLSX, пропуски, дубликаты, некорректные числа, пустые файлы, неподдерживаемый формат).

## Этап 3. Интеллектуальный микросервис (24.10 – 31.10, параллельно с этапами 1–2)

- Контракт `/analytics/v1` (Pydantic), проверка `X-Service-Key`, `health`, `capabilities`.
- Конвейер и реестр методов.
- Методы по порядку приоритета: предобработка → аномалии (robust_z, zscore) → корреляции → тенденции → кластеризация (k-средних, силуэт, PCA) → прогноз (naive, SES, Holt; выбор по ошибке на отложенной выборке).
- Статус по каждой процедуре: `ok` / `skipped` / `error` с понятным сообщением.
- `signals` для сводной оценки.

**Тесты:** unit на каждый метод (известный ответ на малых данных, граничные случаи: постоянный ряд, MAD = 0, пропуски, n меньше минимума); контрактные тесты схемы ответа; проверка воспроизводимости (два одинаковых запуска дают одинаковый результат).

**Статус (22.10.2026): выполнено в объёме задания этапа.** Отдельные модули: проверка данных, аномалии (медиана/MAD, порог, MAD=0), Пирсон, k-средних + StandardScaler + силуэт, SES, оценка 0–100. Контракт `/analytics/v1`, Pydantic, health, capabilities, ошибки, логирование без значений показателей. Документация: `docs/ANALYTICS_API.md`. Вызов из backend (этап 4) не входит в этот объём.

**Тесты:** integration backend ↔ ML (ML-сервис доступен; недоступен → понятная ошибка, данные целы; ошибка одной процедуры → частичный результат); ручной сквозной сценарий UC-0 → UC-1 → UC-2 → UC-3 → UC-4.

**Статус (22.10.2026): backend-часть этапа выполнена.** Адаптер `analytics_client` (тайм-аут, повтор GET, предохранитель, лимит тела, проверка JSON). `AnalysisService` создаёт запуск, вызывает `/analytics/v1`, сохраняет параметры и результаты, статусы `completed` / `partially_completed` / `failed`. Эндпоинты запуска и повторного просмотра комплексного анализа, аномалий, корреляций, кластеров, прогноза и оценки. При недоступности ML — `503` и запись `failed`, без фиктивного успеха. Интерфейс `/dashboard` и мастер на клиенте — в оставшейся части этапа 4.

**Документация к точке:** разделы 4.3.1–4.3.8 по фактической реализации; раздел 4.4.1 (стратегия и план тестирования); плакаты 6.2–6.6.

## Вопросы для согласования с руководителем

1. **MATLAB или Python.** В ПЗ (разд. 1.5, с. 37) основной средой указан MATLAB. Предлагается Python-микросервис (вариант А, обоснование — раздел 0 ARCHITECTURE.md). Допустим ли вариант А, или нужен вариант Б (MATLAB как среда проверки результатов)?
2. **Разные физические узлы.** Достаточно ли для демонстрации трёх виртуальных машин или ПК в одной сети? Допустим ли запуск на одной машине на разных портах во время защиты, если узлы показаны в руководстве по развёртыванию?
3. **Пароли «в зашифрованном виде».** Устроит ли хеширование Argon2id (необратимое преобразование, что строже шифрования) как выполнение п. 3.4.2? Предлагается дать обоснование в разделе 4.3.8.
4. **Шифрование хранимых данных.** Достаточно ли комбинации: шифрование исходных файлов и резервных копий AES-256-GCM, BitLocker для каталога данных PostgreSQL, TLS к СУБД? Или требуется шифрование числовых значений в столбцах БД (это ограничит SQL-агрегирование)?
5. **Пользователи и роли.** В ПЗ один основной пользователь — специалист. Нужна ли роль администратора (управление пользователями)? Как появляются пользователи: самостоятельная регистрация или создание администратором (скриптом)?
6. **Где считается сводная оценка (формула 7).** Предлагается: статистические признаки — в ML-сервисе, веса, направления, пороги и шкала риска — на сервере как бизнес-логика. Согласуется ли это с требованием «классическая бизнес-логика только на серверной части»?
7. **Формат и структура входных данных.** Подходят ли CSV и XLSX в «широком» формате (строка — период, столбцы — показатели, необязательный столбец категории)? Какая детализация периодов обязательна: только месяц или ещё квартал и год?
8. **Расчётный объём данных** (для PER-3 и LI-7). Например, до 120 периодов × 30 показателей × 10 категорий на набор. Нужна ли конкретная цифра в ПЗ?
9. **Подоценки на референсе интерфейса.** На изображении сводная оценка разбита на «Финансовую устойчивость», «Ликвидность», «Деловую активность» и «Рентабельность». В ПЗ таких групп и расчётных коэффициентов нет. Использовать вместо них группы показателей из справочника (финансовые и операционные) или добавить расчётные коэффициенты (например, рентабельность продаж = прибыль / выручка) как дополнительное улучшение?
10. **Раздел «Отчёты» на референсе.** Экспорта отчётов в ПЗ нет. Реализовывать ли экспорт в PDF или XLSX (дополнительное улучшение) или заменить раздел «Историей анализов»?
11. **Версия Python.** 3.13 (стабильная поддержка научных библиотек под Windows) или 3.14 (актуальнее на январь 2026, но поддержка части библиотек могла быть неполной). Предлагается 3.13.
12. **Вспомогательные зависимости вне заданного стека:** React Router, httpx, psycopg, openpyxl, cryptography, argon2-cffi, PyJWT, nginx, Docker Compose. Нужны ли отдельные обоснования в разделе 4.3.2?
13. **Исправления текста ПЗ** из раздела 1.5 ARCHITECTURE.md (два перечня FR, формула 6, ссылки [10]/[14] и [18]/[19], заголовки табл. 2.8). Согласовать, какой перечень FR считать основным (предлагается табл. 2.9).
