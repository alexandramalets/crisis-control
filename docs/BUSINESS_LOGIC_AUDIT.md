# Бизнес-логика Crisis Control (фактическая реализация)

Документ описывает поведение **текущего кода**, а не пожелания. Сопутствующее руководство: [USER_GUIDE.md](USER_GUIDE.md).

## 1. Назначение

Программное средство аналитической поддержки антикризисного управления. Оно не определяет банкротство и не принимает решения вместо специалиста.

Сквозной контур:

```text
Вход → выбор организации → загрузка данных (версии) → проверка качества
  → исследование (validate, ratios, anomalies, trends, correlation, clustering, forecast, assessment)
  → оценка, проблемы, рекомендации → мероприятия → сценарии / нормативы
  → повторное исследование и сравнение
```

## 2. Роли и доступ

| Роль | Что может |
|---|---|
| Администратор системы | Пользователи, организации, каталоги, здоровье системы. Не изменяет данные чужой организации, если не владелец и не сотрудник с правом редактирования. |
| Аналитик | Работа в организациях, где он владелец или член. |
| Владелец организации | Управление сотрудниками и рабочим пространством, загрузка и расчёты. |
| Сотрудник, просмотр | Чтение наборов, исследований, отчётов. |
| Сотрудник, редактирование | Загрузка данных, запуск исследований, рекомендации, мероприятия, сценарии, нормативы. |

Данные организаций изолированы на уровне API.

## 3. Данные

- Справочник показателей задан миграциями (не десять кодов, а расширенный каталог).
- CSV/XLSX, пропуски не заменяются нулями, дубликаты периодов блокируют сохранение.
- Повторная загрузка с тем же именем создаёт новую версию (`version_no`), старая сохраняется.
- Исследование ссылается на конкретный набор (версию).

## 4. Исследование

Стандартный запуск из интерфейса передаёт процедуры:

`validate`, `ratios`, `anomalies`, `trends`, `correlation`, `clustering`, `forecast`, `assessment`.

Параметры аномалий, корреляции (Пирсон/Спирмен), кластеров и прогноза уходят вложенными объектами в аналитический микросервис и не перезаписывают друг друга на корне запроса.

Если данных недостаточно, процедура получает статус «пропущено» с сообщением. Фиктивные значения не подставляются.

Расчёт синхронный: кнопка блокируется до ответа; повторный запуск одним нажатием не уходит.

## 5. Оценка 0–100

Сохраняются:

- исторический балл относительно собственной динамики;
- балл соответствия заданным пользователем границам, если границы есть;
- полнота данных.

Отображаемый `score` — сохранённый результат, без пересчёта на frontend. Если нормативы не заданы, интерфейс явно указывает, что это не отраслевой рейтинг устойчивости. Отсутствие показателя не улучшает балл: пропущенные ряды не входят в среднее.

## 6. Проблемы, рекомендации, мероприятия

Модуль `crisis_engine` на backend формирует проблемы и предупреждения по сохранённым результатам (аномалии, тенденции, оценки, коэффициенты). Рекомендации связаны с проблемами и не создаются заново при каждом открытии страницы.

Мероприятия: статус, срок, ответственный из сотрудников организации, история событий. Просрочка определяется по сроку и незавершённому статусу. Выполненные записи остаются в истории. Динамика показателя до/после, если показывается, не утверждает причинность.

## 7. Сценарии и нормативы

Сценарий меняет выбранные показатели в копии расчёта. Исходный набор и исследование не изменяются. Это условный расчёт, не прогноз.

Нормативы и планы задаёт пользователь (показатель, границы или целевое значение, источник). Отраслевые константы системой не выдумываются. Заданные границы участвуют в оценке соответствия.

## 8. Сравнение, PDF и журнал

- Сравнение двух исследований одной организации: при разных наборах, периодах или версиях сервиса сравнение оценок помечается как некорректное.
- PDF собирается на сервере с кириллицей; пустые разделы опускаются.
- Журнал действий хранит `organization_id`, когда действие относится к организации.

## 9. Ограничения, которые остаются намеренно

- Нет самостоятельной регистрации.
- Нет правки уже сохранённых ячеек набора.
- Нет автоматического «диагноза кризиса».
- Многомерные выбросы Isolation Forest входят в процедуру аномалий и не хранятся отдельной таблицей.
